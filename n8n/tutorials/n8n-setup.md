# Connect n8n to Apify and configure private workflow state

Bind separate GitHub and Apify credentials, set a per-run spending cap and verify private state. The free templates import as inactive. Running a hosted Actor uses your connected Apify account at its published rates. This guide covers recovery when a start times out.

## Set up a private working copy

1. In your own n8n project, create a workflow and choose **Import from File**. Select one of the four JSON files in `workflows/`. Use a separate project or isolated instance, credentials and state repository for each organization. Restrict who may edit, call or execute the workflow.
2. In your private GitHub repository, copy the contents of [the seed file](../fixtures/private-state-seed.json) into `state/merchant-demo.json` on the default branch. Use `supplier-demo`, `migration-demo` or `rss-demo` for the other examples. Seed once per stream. A new production feed, supplier or site gets its own file and scope. The GitHub credential needs Metadata read and Contents read/write on that one private repository. The repository must allow the credential to update this file. Keep this private repository separate from published examples.
3. In n8n Credentials, create two **Header Auth** credentials. For each, enter header name `Authorization` and value `Bearer ` followed by the appropriate customer token. Bind the GitHub credential to **Verify private repository**, **Read state**, **Claim operation**, **Persist run ID** and **Commit verified observation**. Bind the separate Apify credential to the remaining HTTP nodes, including **Load previous source** where present. Grant only the ability to start the chosen Actor and read the customer's run, dataset and key-value records. Store tokens only in the credential manager.
4. In **Configure connection**, replace `owner`, `repo` and `scope` with operator-controlled literals matching the private state file. Review `maxUsd` against your intended purchase and the current public price. Set `enabled = true` only after selecting the credentials. Keep the source events separate from these settings. The JS Code nodes use Node's built-in `crypto` for SHA-256. For a self-hosted task runner, allow the single `crypto` module if required. [n8n Code node](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.code/)
5. To run the synthetic example on your own account, use **Test with one sample**. **Merchant and RSS can incur small charges even for this sample.** The fixed Supplier and Migration demos request zero paid reports. Import alone starts nothing. Free/Paid entitlement comes from the actual Apify account. The workflow checks the run's event counters and the output delivered.
6. On n8n 2.49.7, after configuring credentials and testing the sample, **publish the configured child workflow inside your own private n8n project** so another workflow can call it by ID. This makes that version executable in the project. Marketplace submission is separate. Create an **Execute Sub-workflow** node in a trusted parent in the same project, select the published child, pass **one** item matching the envelope in the product guide, and wait for its result. Feed it from an authorized connector or export-complete event. To run daily, the customer can add a Schedule Trigger to their own parent workflow that retrieves the latest complete export. Use the export's immutable positive, increasing sequence number. A retry of the same export must preserve the same number, contents and cap. Serialize observations per stream in source order.
7. Connect the terminal outputs to the customer's private review, ticketing or approval destination. Use `runId` as the downstream idempotency key. The duplicate output returns the sequence. Retrieve the private journal and last committed run if the downstream system missed its handoff. Only explicitly approved customer-owned downstream steps should ever publish or write operational data. On workflow error, hold the original export and alert the stream owner through their existing private channel.

## Private state and recovery

The state file keeps an increasing high-water mark, an in-flight request fingerprint, an opaque run ID and a pointer plus a SHA-256 fingerprint for the latest eligible baseline. Before another paid comparison, the workflow hashes the recovered source and compares it with the committed fingerprint. GitHub compares the old file SHA on every update. A write conflict stops the losing execution before another submission. Two workers may read the same record, but only the winner can reserve a fresh operation.

Before sending confidential data, set Apify storage access to **Restricted**, disable automatic sharing of runs with the Actor developer and verify access with a synthetic run under your own account. Keep run, dataset and storage identifiers private. Authorized readers can open the raw `INPUT`, `REPORT`, dataset or feed checkpoint. Supplier catalog fields are ordinary Actor input fields. Use only synthetic examples in public issues or support requests.

Review retention for the customer's Apify plan and deletion settings for n8n and the customer's source archive. Keep prior successful Apify records available until at least the next comparison. When the organization's retention period ends, its authorized owner deletes the applicable source, run storage and dataset according to policy. Raw records and reports can also pass through the customer's parent workflows. An expired or inaccessible baseline stops the workflow. Recovery requires the owner to reconstruct the last known good baseline from the private source archive and document a deliberate reseed in a fresh, separately named stream.

After the first terminal status the workflow waits ten seconds and retrieves the same run again before comparing service units with the Apify event ledger. If the final figures remain inconsistent the stream stays locked for reconciliation. [Apify Get Actor run](https://docs.apify.com/api/v2/actor-run-get)

| Situation | What the operator does |
|---|---|
| Same or older committed sequence | Expect `DUPLICATE_SKIP`. Look up the earlier delivery in the private system of record. |
| Known pending run, timed out or still running | Resend the identical envelope and cap. The workflow reads the recorded run instead of submitting another. |
| Intent saved, but no confirmed run ID | Keep the stream locked. Inspect the customer's Apify history and charges in the matching time window. If one submission can be identified with certainty, attach that verified run ID to the existing pending record using a conditional update, then resume. Ambiguity needs operator reconciliation. |
| Failed, restricted, incomplete or unexpectedly billed run | Inspect run, summary and charges. Preserve the old baseline. Once the owner records a terminal resolution, consume the failed sequence in the private journal using the current SHA, leave the old baseline pointer intact and clear pending. A corrected export gets a new sequence and an explicit budget review. |
| Delivery complete but external notification failed | Replay the customer-owned downstream handoff keyed by the original run ID. Look up the private report using the journal. |
| Wrong repository, missing state, modified schema, changed credentials | Correct the customer-specific configuration and review the state before resuming. |

Disable saving production execution payloads wherever the customer's policy requires it. These templates set success, error and manual execution retention off. Upstream workflows, the customer's instance, GitHub journal history and Apify storage each have their own retention settings. Never put raw catalog records, credentials, confidential download URLs or personal data into the journal or a public issue.
